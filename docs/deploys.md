# Deploys

Read before changing `.github/workflows/pages.yml`, `.github/dependabot.yml`, the Pages settings, the `main` ruleset or the Dependabot alerts. Moved from CLAUDE.md and split into bullets, with two updates: `check:head` joined the workflow, and the dev-only `zod` alert (a lint-plugin dependency) was dismissed by GitHub on its own (alert 4, `auto_dismissed`), so there is nothing to dismiss by hand.

- `.github/workflows/pages.yml` runs `lint`, `format:check`, `test`, the GitHub sync, `next build` and `check:head` and deploys `out/` with GitHub's Pages artifact actions on every push to `main`, daily at 09:17 UTC (refreshing the GitHub snapshot; the previous snapshot is restored from the actions cache first, so an API failure keeps the last good data) and on `gh workflow run pages.yml`.
- Settings → Pages → Source must be **GitHub Actions**.
- A red check on `main` means nothing was deployed.
- `.github/workflows/repo-check.yml` is a **separate** workflow (push to `main`, daily 09:41 UTC, `gh workflow run repo-check.yml`) that runs `node scripts/check-repos.mjs`: it compares the public repos you own or contributed to with the ones `projects.js` links and fails when one is missing from the site or a linked one was renamed, archived or deleted. It is separate on purpose: inside `pages.yml` a red run would still deploy, which would break the line above. Per GitHub's docs and community reports (not yet seen on a real failed run here, so check the first red one): GitHub emails a failed run to whoever triggered it (for the daily run, whoever last edited the cron line) if Actions notifications are on in your account settings; `continue-on-error` would turn a failure into a pass and silence that email, so don't add it; and don't make this a required check in the `main` ruleset (it would block pushes). Repos you chose to leave off the site go in `ignore` in `scripts/repo-check.json` as `owner/name: reason` (a bare name matches nothing; ignoring never hides a repo the site links, which is still checked for a rename, archive or 404). The contributed-to half uses GraphQL `repositoriesContributedTo`, which needs the token (`npm run check:repos` locally skips it without `GITHUB_TOKEN`) and asks for the first 100 repos; forks are skipped in both lists (a team repo you work on through a fork needs adding by hand); GitHub's docs say only "recently" and one run showed about the last year, so a repo that drops out of that list is not drift. The Actions `GITHUB_TOKEN` can read that field for your account (the first run, on 2026-11-04, passed with the token set and no skip notice); if GitHub ever refuses it, the run fails red with the error until a personal token is used instead. An API failure also fails the run (a check that could not run should not look green), after up to three tries for a timeout or a 5xx (a 404 or a refused token is not retried).
- There are no pull-request checks.
- Every `uses:` line is pinned to a commit SHA with a `# vX.Y.Z` comment, checkout doesn't persist credentials, both jobs have a timeout, and only the `npm run sync` step gets `GITHUB_TOKEN` (the build runs `npx next build`, since `npm run build` would rerun the sync through `prebuild` without the token).
- `.github/dependabot.yml` opens weekly PRs for the `github-actions` ecosystem only, to move those pins; there is no npm entry, so npm bumps stay by hand (see the lockfile rule in CLAUDE.md).
- `main` has a ruleset that blocks force-push and deletion (switch it off in Settings → Rules before rewriting history), and Dependabot alerts are on (no security-update PRs; the dev-only `zod` alert, a lint-plugin dependency, was dismissed by GitHub on its own).
- GitHub disables scheduled workflows after 60 days with no repo activity, which would silently stop the daily deploy (and the `● now` retirement it drives); `gh workflow enable pages.yml` turns it back on.
- Node version: `.nvmrc`.
