# Accessibility and speed audit: measured (2026-10-29)

Follows `standards-2026-10.md` §3, which deferred these items as "measure first". This note holds the numbers; **no app code was changed**. Primary sources for the standards only. **[inference]** marks reasoning that isn't from a source or a measurement; **[unconfirmed]** marks claims no primary source I found states. All numbers are from 2026-10-29.

## Method

- Lab runs: Brave (headless, `--headless=new`) driven over the DevTools protocol by scratch scripts that copy `scripts/browser-check.mjs`'s server and CDP code. They are not in the repo (they lived in the session scratchpad); the method is written here so a run can be redone.
- `out/` was rebuilt from `fcdd360` before the lab runs (the earlier `out/` was one commit older and one chunk differed from live).
- **The local server sends uncompressed bytes**, unlike GitHub Pages (gzip). Slow-network numbers below are inflated by that: see the caveat on the 404.
- Phone profile: 390x844, 3x DPR, touch, CPU 4x, network 150 ms RTT / 1.6 Mbps (Lighthouse's slow-4G numbers). Desktop: 1291x808. Machine CPU is not recorded; absolute busy percentages are for this machine only, the ratios across throttle rates and states are what carry over.
- Each CWV cell is **one run** (n=1). Treat differences under ~2x as noise.

## Bars (written before measuring)

A candidate becomes a proposed fix only if it crosses one of these.

- Core Web Vitals "good": LCP 2.5 s or less, INP 200 ms or less, CLS 0.1 or less (https://web.dev/articles/vitals).
- JS weight: no bar of its own; lazy-loading counts only if tied to a CWV miss or a long task.
- Target size, WCAG 2.5.8 AA: a target under 24x24 CSS px that no exception covers (https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).
- 2.2.2 Pause, Stop, Hide (A): self-starting motion or blinking, over 5 s, beside other content, with no mechanism (https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html).
- Hero egg: a long task (over 50 ms) while on screen at rest at 4x CPU, or the main thread more than 20% busy at 4x CPU while idle.

## 3. Hero egg cost

The `TODO.MD` claim ("redraws every frame") is wrong in detail: it paints on every other frame.

Method: a `MutationObserver` on the egg's `pre` counted real paints; `Performance.getMetrics` `TaskDuration`/`ScriptDuration` diffs over 10 s idle, after the intro, desktop 1291x808, no input.

| CPU                    | State        | Paints/s | Main thread busy    | Script | Long tasks   |
| ---------------------- | ------------ | -------- | ------------------- | ------ | ------------ |
| 1x                     | on screen    | 30       | 22%                 | 18%    | 0            |
| 1x                     | scrolled off | 0        | 2%                  | 0.1%   | 0            |
| 4x                     | on screen    | 30       | 43% (replicate 50%) | 36%    | 0            |
| 4x                     | scrolled off | 0        | 3%                  | 0.3%   | 1 (51 ms)    |
| 6x                     | on screen    | 30       | 73% (replicate 71%) | 57%    | 0            |
| 6x                     | scrolled off | 0        | 2%                  | 0.1%   | 0            |
| phone-size 390x844, 4x | on screen    | 30       | 38%                 | 33%    | not recorded |

- rAF runs at 60/s; the egg paints on half of them (`useEggGame.js` paints on `odd` frames). It stops completely off screen.
- **All 300 paints in a 10 s idle window were distinct frames.** The egg animates at rest (boil, flame), so "skip a paint when nothing changed" would save nothing; only a lower rate or a cheaper paint would.
- Crosses the bar: busy above 20% at 4x (43-50%). Does not cross the long-task bar. **[inference]** On a real low-end phone the cost is a continuous 40-70% of the main thread while the egg panel is visible, which would show up as battery drain and possibly input latency. The INP runs above stayed under 50 ms, but I did not check that the egg was on screen for every interaction in them.

## 4. Target size (2.5.8)

Method (in-page script): every visible `a`, `button`, `input`, `select`, `textarea`, `summary`, `[role=button|link|tab|menuitem]`, `[tabindex>=0]` and `[data-row]`. Each one under 24 px by its rect is scrolled to the viewport centre and its **effective hit area** is found by sampling `elementFromPoint` around it, so invisible `::before` enlargements count. A target still under 24 px then has the spacing exception checked as code: a 24 px circle on its centre may not reach another target (that really owns the nearest point, not one hidden under a fixed bar) or another undersized target's circle. Nested targets are skipped for the neighbour test; inline-text links are listed for hand classification.

| State (desktop 1291x808)                                                      | Targets | Under 24 px after hit areas | Fail spacing      |
| ----------------------------------------------------------------------------- | ------- | --------------------------- | ----------------- |
| home, gui                                                                     | 33      | 12                          | **4**             |
| help popup                                                                    | 2       | 1                           | 0                 |
| shell popup                                                                   | 36      | 14                          | **4** (same four) |
| terminal mode                                                                 | 20      | 0                           | 0                 |
| project page                                                                  | 16      | 10                          | 0                 |
| `/resume/`                                                                    | 7       | 1 (inline text link)        | 0                 |
| 404                                                                           | 1       | 0                           | 0                 |
| **phone 390x844**, every state tried (home, menu popup, project, resume, 404) | 1-31    | 0-2                         | 0                 |

- **The four failures are one control group:** the project filter's folder rows (`projects/10`, `professional/1`, `hackathon/7`, `personal/2`), each 199x18 px, stacked with no gap. Their circles overlap each other. **[inference]** No other exception (equivalent control, inline, essential) clearly applies; I did not look for a larger control that does the same filtering. On touch these rows are 28 px (`docs/gui.md`), which the phone run matches (0 failures).
- **Everything else under 24 px passes by spacing**: the nav buttons, the bottom bar links and the project-page links are 17-18 px tall but have clear space around them, so the circle test passes. That is the spec working as written (https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), not a gap in my audit.
- `/resume/`'s "download the pdf" is a link inside a sentence (the inline exception).
- On phone, nine targets per page reach 24 px only through `::before` hit areas; remove those and they'd be 17-21 px. **[inference]** They are the reason the phone number is 0.
- **Accordion:** my click on the first experience row did not leave a row expanded, so that state was not confirmed audited. From `Experience.jsx` the expanded details are plain `div`/`span` text with no links or buttons, so **[inference]** it cannot add targets; the target count stayed 33.
- Not audited: vim, the in-shell `./egg`, the hero egg's own controls beyond what the scripts saw.

## 5. 2.2.2 Pause, Stop, Hide: inventory

Measured with a `MutationObserver` over the whole document and `document.getAnimations()`, sampled from 4-8.5 s after load for 15 s.

| What moves or blinks by itself                  | Normal motion                                                            | `prefers-reduced-motion: reduce` | Control on the page         |
| ----------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------- | --------------------------- |
| 404 egg                                         | ~60 repaints/s, still going at 19 s                                      | stops (one frame)                | none; the page has one link |
| hero egg (idle boil/flame)                      | 30 repaints/s, still going at 24 s                                       | **still plays** (by policy)      | none found                  |
| `caret-blink` on the `h1` (home, project pages) | infinite, 1.04 s cycle                                                   | **still blinks** (by policy)     | none                        |
| `press-blink` on a hero button                  | infinite, 1.1 s cycle                                                    | **still blinks** (by policy)     | none                        |
| header and section type-ins, intro              | finite (nothing but the above changed after the intro in any 5 s window) | plays                            | n/a (stops by itself)       |

What the standard says (read 2026-10-29, https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html): the mechanism "may be explicitly provided in the content, or may be relied upon to be provided by either the platform or by user agents". The page does not mention `prefers-reduced-motion`, and does not say whether a browser or OS setting alone is enough. So whether the 404 egg's reduced-motion still frame counts as a mechanism is **[unconfirmed]**. The essential exception needs that removal would "fundamentally change the information or functionality"; **[inference]** the 404's rolling egg is decoration, so it is unlikely to qualify, while the hero egg is the front of a minigame, which may.

## 6. Proposed fixes, ranked (Danny decides; none are started)

Each crosses a bar above. Any fix keeps "reduce, don't remove" for reduced motion (`CLAUDE.md`).

1. **404 egg: give it a stop.** Crosses 2.2.2 (moves forever, no control, and a page-level mechanism is unconfirmed). Smallest options: stop after ~5 s, or a click/key pause. The cheapest of the set, and a single small component (`RollingEgg.jsx`).
2. **Hero egg: lower the idle cost.** Crosses the 20% busy bar (43-50% at 4x). Frames all differ, so the lever is a lower paint rate at rest (for example 30 to 10-15 per s) or a cheaper paint, not skipping duplicates. This also helps the 2.2.2 question for the hero egg; a visible pause control would answer it fully but changes the page's look, so it's a decision.
3. **Folder filter rows: 24 px of room on desktop.** Crosses 2.5.8 (four rows, 18 px, no gap). The phone already does this with 28 px rows.
4. **The two infinite blinks (`caret-blink`, `press-blink`).** Possible 2.2.2 issue but the weakest: **[inference]** a caret that blinks is arguably part of the type-in effect rather than "information"; this is a judgment call, so the bar is crossed only on the plain reading of "blinking" + "over 5 s".

Not proposed (no bar crossed): INP (24-48 ms), CLS (under 0.01), home and project LCP, JS weight and lazy-loading (no CWV miss or long task ties to it; the 404's phone LCP number is uncompressed-server noise until re-measured with gzip). Still open: Lighthouse and its axe audit (needs a way to run it), CrUX, unused-JS coverage, a screen-reader pass.
