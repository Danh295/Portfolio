# Terminal mode and the embedded shell

Read before changing terminal mode, the embedded shell, the phone keyboard handling or shell Enter. Moved from CLAUDE.md unchanged.

- **Terminal Enter**: a focused button or link handles its own Enter (e.g. `[exit] back to gui`, links from `cat contact.vcf`); otherwise Enter runs the prompt. In the gui, typing while the embedded shell is open but unfocused goes back to its prompt instead of firing shortcuts.
- **Terminal mode** (`./app --mode terminal`): `components/shell/Terminal.jsx` + `Vim.jsx`. The screen is `position: fixed` to the part of the screen the visitor can see: `src/lib/useVisualViewportFrame.js` sets `--vv-top`/`--vv-h` (the `visualViewport`) and `data-kb` while a phone keyboard is up (the pure `src/lib/viewportFrame.js` `frameFor` decides, tested with a real iPhone's numbers in `test/viewportFrame.test.mjs`: a keyboard is up only while the prompt has focus AND the visible area is 150px+ shorter than the tallest height seen in this orientation (`nextBaseline`). On an iPhone the keyboard opens in two steps, `visualViewport.height` dropping first and then `innerHeight` itself shrinking while the page scrolls, so `innerHeight − visualViewport.height` is 337 and then 0 and can't be the test; found with a temporary `?vvlog` phone telemetry, commits `26c6b53` and `0b9c5d5`, since reverted: revert the reverts to bring it back), so iOS Safari panning the page to reveal the prompt can't slide the header off the top; with `data-kb` the shortcut bar is hidden (parked below the visible area it still showed in the strip iOS 26 leaves above the keyboard, under Safari's address pill) and the output re-pins to the prompt (`useStickToBottom`). The embedded shell panel uses the same hook (`lock: "keyboard"`: the page locks only while a keyboard is up) and, with `data-kb`, fills the visible area inset 8px. On touch the page doesn't rubber-band (`overscroll-behavior-y: none`: the bounce moved the pinned nav and bar), and both shells' output is 14px with the prompt looking the same: it stays 16px, because iOS zooms the page when a field under 16px takes focus and only reads the computed size, and is scaled to 0.875 (`transform`, from its left edge) so it reads as 14px; its row is the height of a printed line (`line-height` 1.55 × 14px in the embedded shell, 1.6 × 14px in terminal mode), or pressing Enter, which turns it into a printed line, shifted the text by the 3px a 16px line is taller. Typing in or focusing a shell's prompt returns its output to the bottom even after scrolling up (`useStickToBottom`). While a shell has the keyboard up the page is `html.locked`: iOS lets a page with a keyboard open be dragged by up to the keyboard's height (measured: scrollY 0 to 216 under the pinned nav and bar, which teleported), so a locked page takes only pinch zoom (`touch-action: pinch-zoom`), the gui's nav and bar are hidden, and a shell's own scroll box is `pan-y` with `overscroll-behavior: contain` so a drag at its end can't carry on to the page. A fixed body has no document scroll (`scrollY` reads 0 and the document is one screen tall), so `src/lib/pageLock.js` owns the lock: it remembers the scroll position (shifting the body up by it, so nothing jumps behind the shell), puts it back on unlock, and the page can still be moved while locked: `pageScrollY`, `pageMaxScroll` and `scrollPageTo` are `scrollY`, the document's furthest scroll and `scrollTo` for a page that is either scrolled or locked (`alignTarget`, `scrollSec`, `parkEgg` and `keepAligned` use them), so the shell's `cd` moves the page behind the open shell at once (instantly: a locked page can't animate) and keeps the shell open, and `./egg` scrolls from where the page is. Before that, on a phone `./egg` scrolled from the top of the page and `cd` went nowhere (its target was clamped to the one-screen locked document, and the jump did nothing until the shell closed). The browser check fakes the keyboard by overriding `visualViewport.height` and firing its `resize`, which drives the real lock. A keyboard still counts for 700ms after its prompt loses focus (iOS hands the screen back about half a second later; treating that gap as 'no keyboard' flashed the layout). A headless browser can't open a keyboard: the browser check sets those variables by hand, and the real iPhone check covers the rest. The embedded shell (`` ` `` key) is `MiniShell.jsx`. Both frame one `ShellPane.jsx`: the output log (`TermLines.jsx`, `role="log"`) and the prompt under it, kept pinned to the latest prompt (`src/lib/useStickToBottom.js`), with a click focusing the prompt unless it ended a drag-select; `variant` (`term`/`embed`) picks the prompt text (`promptText` in `spec.js`, shared with past prompts), labels and sizing. Both shells' state and keys (sessions, history, autotyped shortcuts, the inline ./egg) live in `components/shell/useShell.js`; a command's effects on the page (open a project, theme, scroll to a section…) come back to App through `onFx` → `applyFx`.
